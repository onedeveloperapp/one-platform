# @flyee/db

The ONE database: hand-written SQL migrations with Row Level Security on every table, a pgTAP suite, and a Drizzle mirror generated from the migrations.

Many firms share this database and never see each other. A firm is an `organizations` row; every table that belongs to a firm carries `org_id`, and its policies ask `is_org_member()`.

## The baseline

`migrations/` holds the ONE baseline, written in M1 for a new Supabase project. The ONE development project has had it since 2026-10-21, so every change is a new file (0043 on), and a file a hosted database applied is never edited again.

## Conventions every migration follows

- **Secure by default.** Nothing in `public` is reachable by the API roles unless the migration grants it: an explicit `grant` beside each table's policies, RLS on every table, and for every function `revoke all ... from public, anon` followed by an explicit `grant execute`. PostgreSQL grants EXECUTE to PUBLIC by default, so the revoke is never optional.
- **The firm is on everything.** A table of firm data carries `org_id`; a function that reads or writes firm data takes the firm as an argument and checks membership. `current_org_id()` is only for what is about the person.
- Who belongs to a firm, and anything a person decides in it, changes through an audited function, never a direct write. Functions that give or take access call `require_aal2()`.
- Definer functions pin `set search_path = public`.
- Consent and money tables get `select public.enable_row_versioning('public.<table>')`. A table whose rows hold a client's words keeps them out of its versions with a trigger of its own (`approvals`: `audit_approval_version` leaves out the answer as approved and the words of the decision, which a row version would hand to the operator and keep after the row is gone).
- A file is recorded by its full name (`NNNN_name.sql`) in `public.schema_migrations`; never rename one that a database already applied.
- Every behaviour worth keeping gets a pgTAP file in `tests/` (`NNNN_name.test.sql`, wrapped in `begin` … `rollback`), **with two firms in it**: what is done for one must be shown not to reach the other.
- People in fixtures are invented: never a real name, CPF, e-mail or case number.

## Tests that read the catalog

Three files cover what nobody remembers to cover, because they read the system catalog instead of a list:

- `tests/0003_two_firms_isolation.test.sql`: every table with an `org_id` must have a row of both firms in its fixture (the test fails when a new table has none), and a person of one firm reads zero rows of the other in each of them.
- `tests/0012_grants_catalog_scan.test.sql`: a table or function that becomes reachable by `anon`, a table without RLS, a table a session may write without a policy, or a definer function without a pinned search path fails it.
- `tests/0009_account_deletion.test.sql`: a new `NO ACTION` or `RESTRICT` reference fails until the deletion decides what to do with it.
- `tests/0012_grants_catalog_scan.test.sql` also holds three rules that came with the vault: the sealed tokens are reachable by no API role, not even the service role; every table of firm data is fenced against a support visit or named with the reason it is not; and no column is named for a lawyer's own credential.

And one script covers the other side: `npm run check:db-refs` reads every `.from()` and `.rpc()` in the code and fails when a table, a column, a function or an argument name is not in the migrations.

## Running the tests

Three ways, same migrations and same tests:

```bash
npm run test:db:embedded   # no Docker: embedded PostgreSQL 17 + a Supabase stand-in (first run installs it into .cache/)
npm run test:db:roundtrip  # the same database, then the app's own code over it: a conversation in and out, a filing package, the DJEN read by days
npm run db:start && npm run test:db   # local Supabase via the CLI (needs Docker)
npm run test:db:remote     # against DATABASE_URL (see the remote section)
```

`scripts/db-embedded/run.mjs` also takes `--only <name>`, `--no-tests`, `--sql <file>` and `--keep`. CI runs the embedded suite on every pull request.

## Applying to a hosted project

`scripts/remote-db-gate.mjs` reads `DATABASE_URL` from `apps/web/.env.local`, then `apps/web/.env` (or `ONE_ENV_FILE`), and refuses localhost targets:

```bash
npm run db:plan:remote     # read-only list of pending migrations
npm run db:migrate:remote  # transactional migrations under an advisory lock
npm run db:gate:remote     # migrate, then run pgTAP
```

On an empty project it bootstraps `public.schema_migrations` and applies the whole baseline. It refuses a database that has a product schema without history, or a history naming files this repo does not have. **Run it only against an ONE Supabase project**: the root `CLAUDE.md` has the safety rules.

## The Drizzle mirror

`src/schema/schema.ts` and `relations.ts` are generated from the migrations, never edited by hand:

```bash
npm run db:schema:pull     # applies the migrations to the embedded server and runs drizzle-kit pull
```

## Usage

```ts
import { createDb, organizations } from "@flyee/db";

const db = createDb(); // uses DATABASE_URL (Supabase pooler, port 6543)
const firms = await db.select().from(organizations);
```

**RLS caveat:** `createDb` connects with the `DATABASE_URL` role and bypasses RLS when that role is privileged. Use it in trusted server code only and scope queries by firm. Browser and user-scoped access go through the Supabase client from `@flyee/auth`, which enforces RLS through the user's JWT.
