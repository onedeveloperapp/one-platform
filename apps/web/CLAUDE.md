# ONE web (apps/web)

Next.js 15 (App Router) + React 19, the only app of ONE: the firm's area, the operator consoles, checkout, auth and the public site. See the root `CLAUDE.md` and `docs/ONE-PLANO-DESENVOLVIMENTO.md`.

> **State in M1 (sprints S1 to S3 built, 2026-10-09).** The database is ONE's own baseline: a firm, its team, invitations, registrations at the bar, AI runs and approvals, the vault, files and issued documents, and each firm's WhatsApp. On top of it: sign-up that founds a firm or accepts an invitation, the team screen, the gate of the logged area, the approval queue, the conversations, the connections, a home that says what needs somebody today, and the operator consoles. One area still carries the previous product's data model and is rewritten in M3: the billing ladder (one-time access plus subscription, USD through Stripe, the entitlement keys of `@flyee/billing/entitlements`). Do not extend it: build ONE's subscription in its milestone.

## Stack and conventions

- **UI**: MUI v9 is the base. Before building a component, look for a MUI or MUI X equivalent among MUI X's community packages (MIT: Data Grid, Charts, Date Pickers, Tree View) and Lab. No component that needs a paid licence: the lint refuses `@mui/x-*-pro`, `@mui/x-*-premium` and `@mui/x-license`, and what only a paid tier gives is built here. Icons: **Phosphor** through the `@/icons/nexture/*` tsconfig alias (real adapters plus Nexture fallback stubs, see `src/icons/README.md`); never import an icon library directly. Import the one icon you render; `src/icons/icon-registry.tsx` (icons by NAME, for the dashboard menu) imports the whole set and ships all of it to any client component that imports it.
- **Styling**: MUI theme driven by CSS variables (`hsl(var(--token))`) from `@flyee/design-tokens`. Component overrides live in `src/style/**/*.css` inside CSS layers (`theme, base, mui, components, utilities`). Tailwind 4 for layout utilities, merged with `tailwind-merge`. Run `npm run check:mui-classes` after touching `src/style/**`.
- **Themes**: one locked palette (`theme-blue`, provisional for ONE) × light/dark, as classes on `<html>`. The tokens are scoped to those classes, so the root layout renders them on the server (the palette and the default mode) and a script in `<head>` corrects the mode before the first paint for a browser that stored another choice; `src/theme/theme-provider.tsx` keeps them in sync afterwards and applies only a palette listed in `THEME_OPTIONS`. Never leave the classes to a client effect: until it ran, the page had no palette at all.
- **Fonts and shapes** (the design system of MedChina's clinical-source home, chosen by the owner on 2026-10-26, the colours left as they were): Mulish (`--font-body`), Urbanist (`--font-heading`; `font-display` falls back to it; that page's own face, TT Chocolates, is commercial and no licence of ONE's covers it) and JetBrains Mono (`--font-mono`). MUI `h1`/`h2` and the display scale are ExtraBold, `h3`–`h6` and any heading below the display scale Bold, a little tight; buttons are bold; an eyebrow is `text-xs font-eyebrow tracking-eyebrow uppercase`. The radius scale, the shadows and the card's hairline are tokens of `packages/design-tokens/css/common.css` (controls 8 to 12px, cards 28px; `docs/DESIGN.md`). Change the faces only when the owner asks.
- **Forms**: Formik + Yup. Semantic data (phone, CPF/CNPJ, CEP, money) uses `components/product/fields/*`, never a raw `TextField`; persist digits, never masks.
- **i18n**: next-intl; every user-facing string goes through messages. ONE is written in **pt-BR only**: one catalog, `packages/content/messages/pt-BR.json`, with the namespaces `marketing` (public site), `auth`, `product` (logged area, billing, settings) and `dashboard` (chrome and menu). `LOCALES` (`src/constants.ts`) is a list of one, and every per-language table is a `Record` over it (`i18n/request.ts`, `lib/seo.ts`, `lib/messages/bell-copy.ts`, `packages/email/src/copy`), so a second language is a data change the compiler walks you through. `node scripts/prune-messages.mjs --check` fails on keys no code renders and on keys the code renders that the catalog lacks; `src/lib/i18n/messages.test.ts` refuses a blank text.
- **Admin copy is hardcoded pt-BR**, outside i18n: the operator surface has one reader. Code comments stay in English; a database value (enum, slug, status) is mapped to a label (`lib/admin/labels.ts`), never shown raw.
- **Which language a request is in**: Portuguese. A public page still carries the locale in its internal URL (`app/[locale]/`, the middleware rewrites `/contato` to `/pt-BR/contato` and redirects the prefixed address back), and `i18n/request.ts` reads it from there; everything else renders in the default locale. There is no language cookie, no detection and no switch.
- **Path alias**: `@/*` → `./src/*`. **Brand**: identity comes from `@flyee/content` (`src/brand.ts` re-exports it); the logo is the single component `src/components/logo/logo.tsx`, which references the provisional ONE SVGs in `public/brand/one-*.svg` (light-surface and dark-surface files; `tone="contrast"` on the deep band) and never redraws them. The favicons, the square mark and the home-screen tile are generated from the mark: `npm run brand:assets`.
- **Remote data**: `lib/remote-state.ts` (`RemoteState<T>`: idle, loading, success, empty, error). An error is never rendered as empty.

Limits are data on the plan rows: `assentos_max` is the seat ceiling the team screen shows and the invitation functions enforce. `components/product/gate-notice.tsx` renders the gate states; `components/layout/menu/plan-indicator.tsx` shows the tier.
- **Sign-up**: one person is one account, and `handle_new_user` creates the profile and nothing else. `/auth/callback` sends an account with no firm to `/auth/complete-profile` (or back to the invitation link it came from), where it accepts an invitation addressed to its confirmed e-mail (`my_firm_invitations()`) or founds a firm (`create_firm`) and becomes its owner. The campaign that brought a founder is attached to the firm at that moment (`lib/firm/actions.ts`), never at sign-up.
- **Usage events**: `lib/product-events.ts` (browser, only offers shown and clicked; it terminates the PostgREST builder with `.then()`, because a bare `void supabase.rpc(...)` never sends the request) and `lib/product-events-server.ts` (`trackServerEvent`, everything that counts toward a metric: `firm.created`, `invite.accepted`, the purchase events). The vocabulary and the allowlist of properties are in migration 0007: events, never content.
- **No tracker runs inside the logged area**: it shows client names and case numbers. The Pixel and GA4 exist on the public site only.
- Reusable blocks live in `components/product/*` and are listed in `components/product/catalog.json` (injected by the `product-screen-guard` hook). Every zero-data view uses `EmptyState`.

## Platform admin and account

- Superadmin area at `src/app/(dashboard)/admin`: `layout.tsx` is a server gate on `profiles.is_superadmin` (RLS stays the real defense); the Admin menu group renders only for the platform operator (`canAccess: { operator: true }`, `lib/firm/menu.ts`). Consoles: `/admin` (the counters of `admin_metrics()` and a tile per console), `/admin/escritorios` (firms), `/admin/leads`, `/admin/billing`, `/admin/ai` (cost per firm, per task and per model; the measure of each task, with the next version of its instructions and its autonomy written there; the categories of the AI's triage of publications, each let out of the shadow with a sample where it met the goal or put back, `components/triage-policy-card.tsx`; the executor check; the model price list), `/admin/calendario` (the forensic calendar every firm's deadlines are counted over: which years of each court were checked against the court's act, the days of a court and year, the acts of the list with their days; a change counts again the court's open deadlines whose count goes through the days it changed; `lib/admin/calendar.ts`), `/admin/audit` (audit trail + sign-in log), `/admin/backups`, `/admin/announcements`, `/admin/help`, `/admin/blog`, `/admin/support`.
- **Console shape**: `page.tsx` is a server component that reads through `lib/admin/*` inside `loadConsole()` (`lib/admin/session.ts`: the operator's session, `ready | error | unavailable`, so a failed read is never an empty list) and hands plain props to a client view; writes are server actions in the console's `actions.ts` that call `requireSuperadmin()` again (a server action is a public endpoint) and record an audit event; the database function that owns the rule is the one doing the write wherever one exists. Formatting is `lib/admin/format.ts` (pt-BR, Brasília clock, money per currency, never summed) and every database value becomes a word through `lib/admin/labels.ts`.
- **Firms** (`/admin/escritorios`, `admin_firms_overview()` / `admin_firm_dossier()` / `admin_people_without_firm()`, migration 0012): one row per firm; the tiles are the filters and count the same flags the rows carry (`lib/admin/firms.ts`). The dossier shows the ACCOUNT of a firm (team, invitations, what it may use, money, consents, sign-ins), never what the firm keeps in the product. The escalated actions act on a PERSON, from the menu of each person in the dossier or in the tab of accounts without a firm (`components/person-actions.tsx`): support access, reset 2FA, the superadmin role, ban and account deletion; ban, 2FA and deletion need `SUPABASE_SERVICE_ROLE_KEY`.
- **Leads** (`/admin/leads`): status tiles (confirmed, waiting, opted out), opt-out, erasure (`purge_lead`) and an export of confirmed, not opted-out contacts as a Resend contact CSV, audited. "Escrever para a lista" writes a message (Markdown), shows who would receive it before sending, and delivers it in batches (`newsletter_sends`, `lib/newsletter.ts`); a send that stopped is resumed from the same screen and never repeats a reader. Without an e-mail provider the screen says so and the button is off.
- Every mutation records an audit event through `lib/audit.ts` (`recordAudit`). Sign-ins are logged by a database trigger; people see their own in `/settings/security`.
- **Granting the superadmin role** (`set_user_superadmin(user, value, note)`): the flag is fenced by a trigger on `profiles` keyed on WHO is asking (`is_superadmin()` reads the database), because a self-`PATCH` of `is_superadmin` would otherwise promote any signed-in user. Self-change is refused in both directions. A session with no JWT (service role, migration, psql) passes: that is how the first superadmin is made.
- **Support impersonation** (`lib/impersonation-actions.ts`, started from `/admin/escritorios`, which a visit returns to): the operator works inside an account through a **parallel session cookie** (`@flyee/auth` `authCookieName`, marker `one-impersonating`), so leaving deletes a cookie and never strands the operator. Load-bearing: the write fence is in the DATABASE (`is_impersonated()` matches the JWT `session_id` against `impersonation_sessions`; triggers refuse writes to consent, the team tables and grants, and the team functions refuse it by name), and it never expires; ending a visit uses `signOut({ scope: "local" })`, never the global default; starting requires the operator's own session at AAL2; credentials and `/admin` are blocked in the middleware. A reason is required, the person is notified, and the access is labelled as support in their sign-in history. Duration lives in `platform_settings` (`impersonation`).
- **Account deletion** (`admin/escritorios/components/delete-account-dialog.tsx`, server action `deleteAccount`, RPC `admin_delete_account(user, confirm_email, reason)`): the unit is the person plus the firm they alone belong to; a person who is one of several in a firm is removed and the firm stays; the owner of a firm with other people in it is refused until the firm is handed over. The order is fixed: re-read the preview, cancel any live provider subscription (a failure deletes nothing), run the RPC in one transaction, then remove storage files through the Storage API using `admin_orphaned_account_storage`, which refuses anything still alive. Refused in the database: yourself, any superadmin, a support session, a live provider subscription. The audit event `admin.account.deleted` survives with counts only.
- **AI runs** (`lib/ai/*`, migration `0016_ai_runs`): a task goes through a model in one way, `runFirmTask(request)` in `lib/ai/executor.ts`, which wires the executor of `@flyee/ai/runs` to the database store (`lib/ai/run-store.ts`, the service role behind `start_ai_run` and `finish_ai_run`, never handed out). It records the run with its prompt version, the hash of the input, the answer and the cost, and puts the answer in the firm's queue when the task asks for a person. Never call a provider directly from a page, a route or a job: a call outside the executor is not recorded, not priced and not approved. `AI_FAKE_PROVIDER=1` makes the fake provider answer every task on a machine with no key (model name `fake`, ignored in production). `lib/ai/jobs.ts` gives up the runs nobody finished.
- **The vault** (`lib/connections/*`, migration `0017_connections`): `getVault()` is the one way to a firm's vendor token, for jobs and webhooks only. Open a token once per batch of work, naming the firm and a purpose (`vault.open({ orgId, connectionId }, "whatsapp.send")`): every open is audited, and a connection of another firm is not found. A page never opens a token, and a secret never goes into `connections.metadata`.
- **Files** (`lib/files/*`, migration `0018_files_documents`): `startUpload` (the person's session reserves, the backend mints the signed upload URL), `finishUpload` (the backend measures and keeps or rejects) and `downloadUrl` (a signed URL of a minute). The bytes never pass through a route of the app. Never read or write the `firm-files` bucket in another way.
- **Issued documents** (`lib/documents/*`): `issueFirmDocument(input, render)` is the one way a document is issued; the renderer prints the verification mark with `stampVerification`. `lib/documents/verification.ts` holds the pure rules of the public page.
- **WhatsApp** (`lib/whatsapp/*`, `@flyee/whatsapp`, migration `0019_whatsapp`): every delivery enters by one door, `handleDelivery(rawBody, signature)` in `lib/whatsapp/inbox.ts`, used by the webhook route and by the simulator alike: it tells whose signature the delivery carries (the vendor's app secret, or the simulator's own, which is drawn per process and never leaves it), parses, and `applyEvents` (`lib/whatsapp/events.ts`, pure and unit-tested) routes each event to its firm within that provider. A person's message goes out in two halves: `sendMessage` (`lib/whatsapp/actions.ts`) reserves it under the person's session, then `deliverOutbox` (`lib/whatsapp/send.ts`) claims and sends it and records what the vendor answered; `lib/whatsapp/jobs.ts` sweeps what was left behind and brings pending media into the firm's files (`lib/whatsapp/media.ts`). `providerFor` (`lib/whatsapp/provider.ts`) is the one way to a number's provider: it opens the firm's token from the vault for the work at hand. Never call the vendor, or write a `wa_*` table, in another way. An action has two halves, and only the person's is fenced by the database: before the backend's half does anything for a connection (open a token, call the vendor, record a simulated delivery) it asks the session the same two questions (`lib/whatsapp/session.ts`: not a support visit, the second factor confirmed). `WHATSAPP_SIMULATOR=1` turns on a number that exists only here (ignored in production). The vendor's browser SDK loads only on `/settings/connections`, and only after the person asks to connect: the logged area carries no third-party script otherwise.
- **AI spend** (price list at `/admin/ai`): every run that reached a provider records one `ai_spend` row, charged to the firm it was made for, written by the backend only, inside `finish_ai_run`. Prices are configuration (`platform_settings` key `ai_prices`, per million tokens), shipped empty; an unpriced model reports `priced = false`, and the console shows the unpriced count beside every total. Cost is stored in USD micros and converted only with an operator-set rate.
- `/admin/backups` (`@flyee/backup`): nightly cron plus "Run backup now" (inline fallback without Inngest). Archives land in the private `backups` bucket; downloads are signed URLs.
- Account plumbing is real: the header bell reads `notifications` (create rows server-side with `lib/notifications.ts`), announcements render in the dashboard layout with per-user dismissal, `/settings` edits the profile (avatar in the `avatars` bucket) and credentials. The quick-support widget (`components/support/support-widget.tsx`) reads the channels from `platform_settings` (`support`, edited at `/admin/support`), falls back to `BRAND.support`, and renders nothing until a human channel exists.

## Messages: bell, e-mail and scheduled jobs

- **Every message to a person is written in Portuguese**, by one copy object per channel: bell texts in `lib/messages/bell-copy.ts` (stored text, written by `notifyLocalized` in `lib/notifications.ts`), e-mail copy in `packages/email/src/copy/pt-BR.ts`. Both are typed so a second language would have to match the Portuguese object. Never write a sentence for a person at a call site.
- **A plan is called by `plans.name`**, never by a word in the copy. A date and an amount arrive already formatted for the reader (`lib/messages/format.ts`: the reader's time zone, `America/Sao_Paulo` when unknown).
- **Claim, then send.** A job that writes to people may run twice. The database marks the row in the statement that returns it (`claim_term_end_notices`, `claim_newsletter_batch`) and only then the message leaves. Where there is no row to mark, the bell's unique `source_key` is the fence (the welcome) and the e-mail goes only to who got a NEW bell row. A message may be lost to a failed send, never sent twice. A batch the provider refuses is given back (`settle_newsletter_batch`), so the next run tries it again.
- **Without `RESEND_API_KEY` nothing breaks**: senders return `{ sent: false }` with no error, the bell still rings, and a job does not claim what exists only as e-mail (a batch of the list). Without Inngest, what an action starts runs in the request (`startNewsletterDelivery`), and nothing scheduled runs.
- **What a reader can stop**: the news (`profiles.marketing_email_opt_out`, the switch in `/settings`) and the messages to the list (`leads.opted_out_at`). Those carry `unsubscribeUrl(...)` in the body and as `List-Unsubscribe` (one click). `/api/public/email/unsubscribe` acts on POST only; a GET moves the request into an httpOnly cookie and lands on `/descadastro`, which asks with one button, because mail scanners open every link they deliver. Receipts and notices about the account ignore the preference.
- **Jobs** live in `lib/*-jobs.ts` and are listed in `app/api/inngest/route.ts`; a function missing from that list never runs. Today: `billing-jobs` (settlement, maintenance, the end-of-term notice), `newsletter-jobs` (one step per batch), `maintenance-jobs` (event rollup and purge), `lead-jobs`, `ai/jobs` (runs nobody finished), `connections/jobs` (the vault's upkeep), `files/jobs` (reservations and orphans), `whatsapp/jobs` (the outbox sweep every two minutes, pending media every five and on demand), `publications/jobs` (the reading of the DJEN every five minutes and on demand, one registration at a time, the shadow triage every five, and ONE's reading of what a person triaged as a deadline or a hearing every five and on `one/publication.read`, `lib/publications/reading-work.ts`; each item is claimed and worked on in the same step, so no claim goes stale while a step waits for its turn), and the backup functions of `@flyee/backup`. Function ids start with `one-` and events with `one/` (`packages/jobs/src/index.ts`, client id `one`).
- **Billing notices** go through `lib/billing-notices.ts` and never throw: by the time one runs the database is already right, and a webhook that failed on a bell would be replayed by the provider and reconcile the whole event again.
- **Auth e-mails** (confirmation, password recovery, e-mail change) are sent by Supabase, not by the app: `supabase/templates/*.html`. They are not rendered by any test here and still carry the previous product's texts: rewrite them with the ONE Supabase project.

## Auth
