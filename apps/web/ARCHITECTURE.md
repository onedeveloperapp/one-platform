Read the section of an area before changing it, and update that section in the same change when a mechanism is added or moved. The build log is `docs/HISTORICO.md`.

## The stack in full

- **UI**: MUI v9 is the base. Before building a component, look for a MUI or MUI X equivalent among MUI X's community packages (MIT: Data Grid, Charts, Date Pickers, Tree View) and Lab. No component that needs a paid licence: the lint refuses `@mui/x-*-pro`, `@mui/x-*-premium` and `@mui/x-license`, and what only a paid tier gives is built here. Icons: **Phosphor** through the `@/icons/nexture/*` tsconfig alias (real adapters plus Nexture fallback stubs, see `src/icons/README.md`); never import an icon library directly. Import the one icon you render; `src/icons/icon-registry.tsx` (icons by NAME, for the dashboard menu) imports the whole set and ships all of it to any client component that imports it.
- **Themes**: one locked palette (`theme-blue`, provisional for ONE) × light/dark, as classes on `<html>`. The tokens are scoped to those classes, so the root layout renders them on the server (the palette and the default mode) and a script in `<head>` corrects the mode before the first paint for a browser that stored another choice; `src/theme/theme-provider.tsx` keeps them in sync afterwards and applies only a palette listed in `THEME_OPTIONS`. Never leave the classes to a client effect: until it ran, the page had no palette at all.
- **Fonts and shapes** (the design system of MedChina's clinical-source home, chosen by the owner on 2026-10-26, the colours left as they were): Mulish (`--font-body`), Urbanist (`--font-heading`; `font-display` falls back to it; that page's own face, TT Chocolates, is commercial and no licence of ONE's covers it) and JetBrains Mono (`--font-mono`). MUI `h1`/`h2` and the display scale are ExtraBold, `h3`–`h6` and any heading below the display scale Bold, a little tight; buttons are bold; an eyebrow is `text-xs font-eyebrow tracking-eyebrow uppercase`. The radius scale, the shadows and the card's hairline are tokens of `packages/design-tokens/css/common.css` (controls 8 to 12px; `docs/DESIGN.md`); a card's and a paper's corners are `rounded-xl`, 12px, since the owner's edits of 2026-11-07 (`style/surfaces/card.css`, `paper.css`; write Tailwind's important modifier with no space before it, `shadow-sm!`, which `check:mui-classes` enforces). The menu is a thin rail of icons (`MenuType.Minimal`, 20px icons in 40px buttons, each named in a tooltip), as ADVBox's, by the owner's choice of 2026-11-07; on a phone the menu that opens is the list with the names. Change the faces only when the owner asks.
- **i18n**: next-intl; every user-facing string goes through messages. ONE is written in **pt-BR only**: one catalog, `packages/content/messages/pt-BR.json`, with the namespaces `marketing` (public site), `auth`, `product` (logged area, billing, settings) and `dashboard` (chrome and menu). `LOCALES` (`src/constants.ts`) is a list of one, and every per-language table is a `Record` over it (`i18n/request.ts`, `lib/seo.ts`, `lib/messages/bell-copy.ts`, `packages/email/src/copy`), so a second language is a data change the compiler walks you through. `node scripts/prune-messages.mjs --check` fails on keys no code renders and on keys the code renders that the catalog lacks; `src/lib/i18n/messages.test.ts` refuses a blank text.
- **Which language a request is in**: Portuguese. A public page still carries the locale in its internal URL (`app/[locale]/`, the middleware rewrites `/contato` to `/pt-BR/contato` and redirects the prefixed address back), and `i18n/request.ts` reads it from there; everything else renders in the default locale. There is no language cookie, no detection and no switch.
- **Path alias**: `@/*` → `./src/*`. **Brand**: identity comes from `@flyee/content` (`src/brand.ts` re-exports it); the logo is the single component `src/components/logo/logo.tsx`, which references the provisional ONE SVGs in `public/brand/one-*.svg` (light-surface and dark-surface files; `tone="contrast"` on the deep band) and never redraws them. The favicons, the square mark and the home-screen tile are generated from the mark: `npm run brand:assets`.

## The gate, the menu and entitlements

- **The gate of the logged area** (`app/(dashboard)/layout.tsx`, a server layout over `components/layout/dashboard-shell.tsx`; `lib/firm/gate.ts` reads, `lib/firm/gate-rules.ts` decides and is unit-tested): an account with no firm goes to `/auth/complete-profile`; the platform operator, who works in no firm, keeps `/admin` and `/settings`; whoever `second_factor_required()` names and has no verified factor goes to their own setup (`/configurar`, whose first step is the factor: the firm's for who manages it, the person's own for anybody else; 2026-11-03) and reaches nothing else, the platform operator to `/settings/security?exigido=1`; somebody of a partner of a firm (everybody of a partner owes the factor, 0069) is kept in the partner's area, sent instead to the partner's own setup (`/parceiro/configurar`, migration 0080, found through the registry's `partnerSetupOf` by the partner's kind), whose first step is the factor, and who manages a partner that never answered its setup finds it in place of the partner's home (an agency's first person sent to the security screen got lost there, the owner, 2026-11-03). The middleware writes the path into the `x-one-path` request header for it (`REQUEST_PATH_HEADER`), and stays query-free. It is guidance, not the fence: row-level security and `require_aal2()` in the functions are.
- **The menu by role** (`lib/firm/menu.ts`, unit-tested; `components/layout/viewer-context.tsx`): a menu item says who it is for (`canAccess`: the operator, an account with no firm, who manages the firm, some functions; nothing means anybody of a firm; a child inherits its group's), and the server layout hands the menus who is looking, so each person's menu is right on the first paint. The settings menu follows the same rule. It is guidance, like the gate: row-level security and the database functions decide what a person may read or do.
- **Entitlements**: `hooks/use-entitlements.ts` calls `org_entitlements(org)`, the single answer to what a firm may use. Screens branch on it, never on plan names. Limits are data on the plan rows: `assentos_max` is the seat ceiling the team screen shows and the invitation functions enforce. `components/product/gate-notice.tsx` renders the gate states; `components/layout/menu/plan-indicator.tsx` shows the tier.
- **The menu's states float, and a group's page is a link beside its title** (the owner, 2026-11-07): "Em breve" and the lock of a module the firm did not contract float over the item's top edge at its right end (`CornerTag` `edge`; the owner, 2026-11-08), so "Direito Previdenciário" keeps its line; every submenu, for any kind of user, the operator's "Admin" included, closes once a page is reached and marks that page when opened again (the owner, 2026-11-08); the overview of the modules is "Todos" beside the submenu's title "Módulos" (`OverviewLink`; "Visão geral" beside "Admin"), never the item "Todos os módulos", which took a line and read as one more module.

## The firm, its team and sign-up

- **The firm and its team** (`lib/firm/roles.ts`, `lib/firm/actions.ts`, migration 0003): a membership says a role (`owner`, `admin`, `member`: the firm ACCOUNT) and a function (`socio`, `advogado`, `controladoria`, `atendimento`: the work). A person is in one firm at a time. Every change is a server action that calls the database function taking the firm; no rule is decided in TypeScript. An invitation link carries a random token whose SHA-256 is all the database stores; accepting takes an account whose CONFIRMED e-mail is the invited one. Without an e-mail provider the link comes back to the manager to send by hand. Colleagues read each other through `firm_team()`, never through `profiles`. A query on `memberships` always filters by `user_id`: a member reads every membership of their firm.
- **Sign-up**: one person is one account, and `handle_new_user` creates the profile and nothing else. `/auth/callback` sends an account with no firm to `/auth/complete-profile` (or back to the invitation link it came from), where it accepts an invitation addressed to its confirmed e-mail (`my_firm_invitations()`) or founds a firm (`create_firm`) and becomes its owner. The campaign that brought a founder is attached to the firm at that moment (`lib/firm/actions.ts`), never at sign-up.
- `/auth/complete-profile` (found a firm or accept an invitation)
- `/convite/[token]` (the page behind an invitation link, public by its token, no tracker, no referrer)

## The setups (`/configurar`)

- **The setup never leads away from itself** (the owner, 2026-10-30): `/configurar`, and the home while it asks the setup, holds nothing that takes the person out of a step before the firm is ready to work: no list of modules, no "see more", no link to another screen. A modules line with "Ver módulos" on the setup's first step took the owner out of a setup half done, and was taken off.
- **Nothing in a flow is met half way** (the owner, 2026-11-03): whatever a later step cannot be done without (the second factor, a role, a connection, a fact the database checks) is a step of its own before the first one that needs it, and the flow does not go past it until it is met. ## AI runs and spend

- **AI runs** (`lib/ai/*`, migration `0016_ai_runs`): a task goes through a model in one way, `runFirmTask(request)` in `lib/ai/executor.ts`, which wires the executor of `@flyee/ai/runs` to the database store (`lib/ai/run-store.ts`, the service role behind `start_ai_run` and `finish_ai_run`, never handed out). It records the run with its prompt version, the hash of the input, the answer and the cost, and puts the answer in the firm's queue when the task asks for a person. Never call a provider directly from a page, a route or a job: a call outside the executor is not recorded, not priced and not approved. `AI_FAKE_PROVIDER=1` makes the fake provider answer every task on a machine with no key (model name `fake`, ignored in production). `lib/ai/jobs.ts` gives up the runs nobody finished.
- **AI spend** (price list at `/admin/ai`): every run that reached a provider records one `ai_spend` row, charged to the firm it was made for, written by the backend only, inside `finish_ai_run`. Prices are configuration (`platform_settings` key `ai_prices`, per million tokens), shipped empty; an unpriced model reports `priced = false`, and the console shows the unpriced count beside every total. Cost is stored in USD micros and converted only with an operator-set rate.

## The vault and files

- **The vault** (`lib/connections/*`, migration `0017_connections`): `getVault()` is the one way to a firm's vendor token, for jobs and webhooks only. Open a token once per batch of work, naming the firm and a purpose (`vault.open({ orgId, connectionId }, "whatsapp.send")`): every open is audited, and a connection of another firm is not found. A page never opens a token, and a secret never goes into `connections.metadata`.
- **Files** (`lib/files/*`, migration `0018_files_documents`): `startUpload` (the person's session reserves, the backend mints the signed upload URL), `finishUpload` (the backend measures and keeps or rejects) and `downloadUrl` (a signed URL of a minute). The bytes never pass through a route of the app. Never read or write the `firm-files` bucket in another way.

## WhatsApp

- **WhatsApp** (`lib/whatsapp/*`, `@flyee/whatsapp`, migration `0019_whatsapp`): every delivery enters by one door, `handleDelivery(rawBody, signature)` in `lib/whatsapp/inbox.ts`, used by the webhook route and by the simulator alike: it tells whose signature the delivery carries (the vendor's app secret, or the simulator's own, which is drawn per process and never leaves it), parses, and `applyEvents` (`lib/whatsapp/events.ts`, pure and unit-tested) routes each event to its firm within that provider. A person's message goes out in two halves: `sendMessage` (`lib/whatsapp/actions.ts`) reserves it under the person's session, then `deliverOutbox` (`lib/whatsapp/send.ts`) claims and sends it and records what the vendor answered; `lib/whatsapp/jobs.ts` sweeps what was left behind and brings pending media into the firm's files (`lib/whatsapp/media.ts`). `providerFor` (`lib/whatsapp/provider.ts`) is the one way to a number's provider: it opens the firm's token from the vault for the work at hand. Never call the vendor, or write a `wa_*` table, in another way. An action has two halves, and only the person's is fenced by the database: before the backend's half does anything for a connection (open a token, call the vendor, record a simulated delivery) it asks the session the same two questions (`lib/whatsapp/session.ts`: not a support visit, the second factor confirmed). `WHATSAPP_SIMULATOR=1` turns on a number that exists only here (ignored in production). The webhook and a number connected by token need only `META_APP_ID`, `META_APP_SECRET` and `WHATSAPP_WEBHOOK_VERIFY_TOKEN` (`metaApp`); `META_SIGNUP_CONFIG_ID` is the signup window's alone (`metaPlatform`), so a number never goes deaf because the window is not configured (2026-11-11). The vendor's browser SDK loads only on `/settings/connections`, and only after the person asks to connect: the logged area carries no third-party script otherwise.

## Messages and background work

- **Every message to a person is written in Portuguese**, by one copy object per channel: bell texts in `lib/messages/bell-copy.ts` (stored text, written by `notifyLocalized` in `lib/notifications.ts`), e-mail copy in `packages/email/src/copy/pt-BR.ts`. Both are typed so a second language would have to match the Portuguese object. Never write a sentence for a person at a call site.
- **Claim, then send.** A job that writes to people may run twice. The database marks the row in the statement that returns it (`claim_term_end_notices`, `claim_newsletter_batch`) and only then the message leaves. Where there is no row to mark, the bell's unique `source_key` is the fence (the welcome) and the e-mail goes only to who got a NEW bell row. A message may be lost to a failed send, never sent twice. A batch the provider refuses is given back (`settle_newsletter_batch`), so the next run tries it again.
- **Without `RESEND_API_KEY` nothing breaks**: senders return `{ sent: false }` with no error, the bell still rings, and a job does not claim what exists only as e-mail (a batch of the list). Without Inngest, what an action starts runs right after its answer (`startNewsletterDelivery`), the sweeps run while ONE is used, and nothing runs by the clock.
- **What a reader can stop**: the news (`profiles.marketing_email_opt_out`, the switch in `/settings`) and the messages to the list (`leads.opted_out_at`). Those carry `unsubscribeUrl(...)` in the body and as `List-Unsubscribe` (one click). `/api/public/email/unsubscribe` acts on POST only; a GET moves the request into an httpOnly cookie and lands on `/descadastro`, which asks with one button, because mail scanners open every link they deliver. Receipts and notices about the account ignore the preference.
- **Background work** (the owner's decision of 2026-11-04): the work a person's action leaves owed (a reading, a check, ONE's answer in a conversation, the next step of a case) is done right after their answer, on the same server, through `soon(label, task)` of `lib/jobs/soon.ts` (Next's `after()`; nested calls work), never through the job runner; each worker's `queue*` or `settle*` does it. What is left (a work that failed, one that waits for an hour of the day, the upkeep) is a **sweep** (`Sweep` of `lib/jobs/schedule.ts`: a key, when the clock runs it (every 5, 10, 15 or 30 minutes, at a minute of each hour, or a time of each day, UTC), whether it also runs while ONE is used, and its `run(service, until)`), declared beside the code it runs (`lib/*/jobs.ts`, `lib/*-jobs.ts`, a module's `jobs.ts` through `lib/modules/jobs.ts`) and listed in `lib/jobs/registry.ts`; a sweep missing from that list never runs. The job runner holds one function, the clock (`one-tick`, `lib/jobs/tick.ts`, listed in `app/api/inngest/route.ts`): a beat every five minutes that runs every sweep due at it in one step (`runSweeps` of `lib/jobs/sweeps.ts`: each on its own, a failure naming only the sweep, nothing started after the beat's time), about 18 thousand executions a month within Inngest's free 50 thousand. The sweeps that serve what people wait on also run while ONE is used (`whileUsed`), once in five minutes on each server, after the answer: `sweepWhileUsed()` of `lib/jobs/while-used.ts`, called by the logged area's layout, the pending center's read, the test chat's read, the client's link and the passenger's agreement link. A sweep claims each work in the database, so the clock, a round while ONE is used and a work after an answer never do anything twice; one that must never run from two servers at once (the DJEN, the tribunal's reading, ANAC's months, the backup, the newsletter) is the clock's only. A sweep's answer holds counts only. No event is sent to the runner.
- **Auth e-mails** (confirmation, password recovery, e-mail change) are sent by Supabase, not by the app: `supabase/templates/*.html`. They are not rendered by any test here and still carry the previous product's texts: rewrite them with the ONE Supabase project.
